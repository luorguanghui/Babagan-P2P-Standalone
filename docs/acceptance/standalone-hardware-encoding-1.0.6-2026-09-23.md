# 独立客户端 1.0.6：H.264 硬件编码与前后台帧率

## 用户实测

安卓接收端两张同一会议截图均显示 VP8：前台到达 58.0、解码 57.3 fps；后台到达 31.7、解码 32.3 fps。两者近似相等，说明接收端解码没有额外丢掉大量已到达帧；问题发生在发送或传输之前。仅凭接收端的 VP8 名称不能判断 Windows 端是否使用硬件编码。

## 编码器对照

- 本机 RTX 4070 Ti / Electron 42.11.6，同一 1920×1080 动态画面经 WebRTC 默认协商为 VP8，`encoderImplementation=libvpx`、`powerEfficientEncoder=false`。
- 优先协商 H.264 后，实际编码器为 `MediaFoundationVideoEncodeAccelerator (NVIDIA H.264 Encoder MFT)`、`powerEfficientEncoder=true`。
- 旧发送参数把 2560×1440→1080p 的缩放比 `4/3` 舍入到 `1.33`，产生 1925×1083 奇数尺寸。集成测试中，这种尺寸出现时 H.264 从 NVIDIA 硬件编码回退到 `OpenH264` 软件编码。保留精确缩放比后，前后台测量均维持 NVIDIA 硬件编码。

## 改动

- 视频收发双方优先协商 H.264，保留 VP8 等格式作兼容后备。若浏览器不支持 H.264 偏好，沿用其默认协商。
- 发送诊断显示实际编解码格式、编码器实现，以及硬件或软件编码状态；无法启用硬件编码时继续共享并提示。
- 发送缩放比保留计算精度，并校正两轴为偶数像素，避免 1.33 或其他屏幕比例、自动画质档位产生奇数尺寸。已用一万组常见尺寸组合做计算校验。
- Windows 防休眠锁通过受限 preload 桥接，在采集轨道启动后启用、共享结束后释放；窗口关闭和导航时也释放。
- WebSocket 若收到服务端“会议结束”关闭事件，观看端直接回到大厅，避免偶发误重连。

## 验证与限制

- 单测覆盖 H.264 偏好、兼容后备、应答端协商、编码器标记和精确缩放。在线双端媒体流程协商到 H.264 并通过共享、语音、停止、重连、结束会议流程。
- 完整 Electron 发送端与 Chromium 接收端测试中，修复后前台发送 1440×810 / 46.1 fps、采集 45.8 fps；最小化发送 1440×810 / 48.8 fps、采集 48.8 fps，前后台编码器均为 NVIDIA H.264 Encoder MFT。该测试场景的瓶颈是采集帧率，不能据此承诺所有场景持续 60 fps。
- 尚未在用户安卓真机上对 1.0.6 重新测量。设备驱动、屏幕内容与网络均可能改变实际帧率或让 Chromium 回退到软件编码；界面以实际编码器统计为准。
- 独立客户端 Node 测试 43 项通过；所改代码与测试文件 ESLint 通过。1.0.6 Windows 便携 EXE 打包成功，解包程序完成在线入会、原生选择器、麦克风、共享防休眠锁释放和结束会议冒烟测试。Android APK 为 `versionCode=7`，v2/v3 签名验证通过，证书指纹与 1.0.5 相同，可覆盖升级。两份安装包均检查了内置 H.264 偏好与偶数尺寸缩放代码。
