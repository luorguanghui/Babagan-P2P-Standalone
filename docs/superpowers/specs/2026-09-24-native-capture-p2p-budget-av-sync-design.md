# Windows 内置采集、多人 P2P 上行预算与共享音画同步

> 1.09 用户修订：撤销本规格原先的房间级总上行硬预算。当前实现只把各连接的 WebRTC 可用带宽估计平均值作为上探参考，保留每连接拥塞自适应，并按所选画质档位设置每人码率及最高增强分辨率。下方“多人上行公平分配”中的房间级预算条款为历史设计，不再作为交付要求。

日期：2026-09-24

## 已确认的目标与约束

- Windows 共享者无需安装 OBS，会议软件在前台、后台及最小化时均能以 60 fps 为目标采集动态屏幕；继续支持屏幕和窗口选择、系统声音、原始比例与动态分辨率。
- 多个接收者时保留 WebRTC P2P / Cloudflare TURN，不增加 SFU、LiveKit 或其他媒体服务器。按共享者总上行预算公平分配每条连接的码率；明确展示实际总上行和各接收者画质。P2P 的总上传量仍随接收者人数增长，不能承诺每个人同时获得 1080p60。
- 重点同步共享画面与共享系统声音。麦克风继续独立，不能把麦克风和系统声音重复播放或错误混音。
- Windows 10/11 x64 仍交付便携 EXE，Android 继续是语音/观看端；原有 OBS 虚拟摄像头与 Chromium 屏幕共享保留为手动回退。
- 当前工作区的既有修改不得覆盖。长期 TURN 凭据仍只在 Worker 端。新采集助手不监听网络端口。

## 方案选择

1. **已选：随 EXE 打包的精简 libobs 采集助手。** 只带 libobs 运行库、`win-capture`、`win-wasapi`、D3D11 渲染库、必要的依赖和数据文件；不带 OBS 主界面、直播/录制插件或虚拟摄像头驱动。libobs 负责显示器/窗口采集、GPU 缩放及系统声音混音；原始 I420 视频与 PCM 音频通过受限本地 IPC 进入现有 WebRTC 轨道。无管理员注册要求，但分发时必须处理 OBS GPL 的许可与相应源码提供要求。
2. **不选：把 Chromium 采集移到另一个始终可见的窗口。** 改动较小，但仍依赖此次降帧的浏览器采集链路；不能把前后台 60 fps 当作稳定行为。
3. **备选：从零编写 DXGI/WGC/WASAPI 助手。** 包体和第三方许可更简单，但要自行处理显示器/窗口、音频时间戳、尺寸变化和设备丢失，开发量及兼容风险更高。若精简 libobs 的正式集成不能满足门槛，再评估此路；保留现有 OBS 输入供有需要者使用。

本机隔离探针已获得更直接的证据：从 OBS 32.1.2 中只取核心和采集插件，约 52 MB 的独立目录（没有 OBS 主界面或虚拟摄像头）在 2560×1440 源、1920×1080 I420 输出下连续 10 秒维持 60 fps、0 滞后帧。原始 I420 管道可传约 180 MB/s。进一步的临时 Electron/WebRTC 本地双端原型中，前台、最小化和恢复阶段的采集、编码及解码均约 59–60 fps，观看端实际显示 1920×1080 H.264。**这仍是约 30 秒的原型结果，不等于长期、系统声音、尺寸切换或 Android 真机验收。**

## 原生媒体桥接与性能门槛

- 精简 libobs 助手与 Electron 通过受同一 Windows 用户限制的本地 IPC 通信。原始 I420 帧使用 libobs 视频时间戳，经上限两帧的队列送入 `MediaStreamTrackGenerator`；追不上实时速度时丢弃旧帧，不能积累播放延迟。30 秒原型已证明此路径可在本机跑满 60 fps，因此先实现原始帧桥接；只在长期门槛失败时再评估助手硬件编码 H.264 → WebCodecs 解码的额外编解码路径。
- 助手报告源尺寸、输出尺寸、帧时间、设备 ID 和结束原因，客户端不得从 UI 预设推断实际尺寸。libobs 源/输出尺寸变化、显示器拔插、窗口关闭和 D3D 设备丢失须产生状态事件。源恢复后连续时间戳，必要时替换轨道并重新计算每个接收者的缩放比例；保持偶数编码尺寸和原始宽高比。
- 性能门槛：在隔离的动态画面测试中，1080p60 目标、主窗口最小化连续 10 分钟，采集与 WebRTC 编码的 10 秒滑窗中位数至少 57 fps，不能持续 10 秒低于 50 fps；相对现有 OBS 输入的额外端到端延迟目标不超过 80 ms。显示分辨率切换后 2 秒内恢复画面，不能泄漏旧 D3D/音频资源。门槛未通过时保留现有 OBS/Chromium 路径，不发布“内置采集已取代 OBS”的安装包。
- 原生助手异常退出时明确提示并停止相关轨道；用户可手动改用 OBS 或旧采集来源。不得静默改变媒体路径或自动上传到其他服务。

## 多接收者上行公平分配

- 采集只做一次，视频轨道复用到每位接收者的 `RTCRtpSender`。新增房间级总视频上行预算 `B`，自动模式按全部连接的实际发送速率、丢包、RTT 与质量限制做慢增快降；设置中提供用户可指定的总上行上限，覆盖自动估计的最高值。
- 每 3 秒按活动视频接收者重新分配：先给每人一个可行的最低份额，再以等权水位分配剩余预算；每人的上限还受其连接带宽估计和编码负载约束。未用尽的份额可分配给其他健康连接。所有 `maxBitrate` 上限之和不得超过 `B`，并保留音频及协议开销余量。新成员加入、成员离开或 TURN 路径改变时平滑调整，避免同时骤升造成排队。
- 现有每连接自适应分辨率继续根据本连接的实际帧率和分配码率独立选择比例。诊断显示总预算、实际总上行、每连接份额、发送分辨率/FPS 与回退原因。测试覆盖 1–4 个接收者、好坏混合网络、成员加入/离开与持续拥塞；确认低带宽接收者不能抢占其他人份额。

## 共享画面与系统声音同步

- libobs 的 `win-wasapi` 输出捕获源采集共享系统声音。原始视频和音频回调的时间戳映射到同一单调时间轴；音频设备变化或采集重建时维持时间连续，不能回退时间戳。麦克风轨道保持独立。
- 共享视频与系统声音在发送侧关联到同一 `MediaStream`，同一接收端 `<video>` 元素播放这两个轨道。麦克风使用独立音频元素或独立音频轨道；不能把系统声音再加到麦克风元素中造成双播。无系统声音时仍正常显示视频。
- 使用 WebRTC `estimatedPlayoutTimestamp` 和测试素材中的同步闪帧/短音测量偏差。健康本地网络下稳定段目标为音画偏差绝对值不超过 150 ms；超过阈值持续数秒时显示可诊断状态并触发有界重同步，不通过无限缓冲换取表面同步。Android 真机和 Windows 接收端均需验收，特别检查暂停、切后台、改分辨率、重连和音频设备切换。

## 实施边界与交付

1. 先做原生采集到 WebRTC 轨道的性能原型并记录帧率、延迟、CPU/GPU、内存和尺寸切换结果。只在门槛通过后写正式采集集成。
2. 将总上行预算算法做为独立可测试模块，随后接入现有 `Mesh` 和 UI；现有 P2P/TURN 信令协议尽量不变。
3. 完成系统音频时间戳、同流传输及接收端合并播放，再执行音画同步自动/真机验收。
4. 更新 README、自动测试、Windows EXE 与签名 APK。Windows 包内含原生助手且不要求 OBS；Android 包维持签名兼容。记录未达到的设备或网络边界，不承诺所有网络可同时为四名接收者提供 1080p60。

## 主要风险

- 把 libobs I420 原始帧送入 Chromium 轨道的长期内存拷贝成本可能抵消独立采集的帧率收益；短时原型成功不能替代 10 分钟门槛。
- 精简 libobs 运行库和插件需要固定版本、核对依赖闭包及履行 OBS GPL 分发义务；不能只复制当前用户的 OBS DLL 而无源码与许可说明。
- libobs 采集源的尺寸变化、HDR、受保护窗口、显示器热插拔和系统睡眠恢复需分别处理。窗口采集帧率会受窗口实际渲染频率限制。
- P2P 公平限额不能降低一对多拓扑所需的总上行次数；用户上行不足时必须降分辨率或帧率。
- 浏览器同步机制不保证所有设备都达到固定偏差；实机测量是交付条件。
